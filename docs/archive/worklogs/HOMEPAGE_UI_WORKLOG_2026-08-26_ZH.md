# 首页与登录态内容工作记录（2026-08-26）

> 归档状态：Historical worklog。本文不描述当前功能完成度；当前状态见 `docs/STATUS_ZH.md`。

## 本次范围

本次仅处理 Symbian 首页、搜索、账号相关列表、评论、动态和消息中心的请求与 UI。播放器、MMF、弹幕、横屏覆盖层及其构建/签名配置均未改动。

本次没有执行编译、打包、签名或设备安装；下列项目需在与其他会话合并后统一验证。

## 问题定义与处理

### 1. 搜索结果与关键词无关

已定位到旧流程虽然请求了 WBI 搜索 URL，但仍以原生 `wiliwili` 请求标识和通用 Referer 请求。该组合可能收到 HTTP 200、`code=0`、却仅含 `data.v_voucher` 的风控凭证响应，并不包含 `data.result`。旧解析器把这种响应当作“成功的空列表”，于是界面没有显示真实错误，用户会误以为返回了无关推荐内容。

处理如下：

- 搜索专用请求档案改为 Web 搜索 UA 和 `https://search.bilibili.com/` Referer，其他 API 的原有请求标识不变；
- 搜索继续经过 WBI 签名，签名准备失败不再退回未签名搜索；
- 2026-08-26 后续线上复现确认：`keyword=%E8%8C%B6%E6%9D%AF%E7%8A%AC` 返回“茶杯犬”相关标题，`keyword=%25E8%258C...` 则返回无关/乱码标题。WBI 签名后的搜索 URL 已是全 ASCII 的单层编码，现直接按字节传入 Symbian HTTP；不再经过 Qt 4.7 `QUrl(QString).toEncoded()`，以避免把 `%` 再编码成 `%25`；
- 解析器必须验证 `data.result` 为数组；识别到 `v_voucher` 时返回明确风控错误；
- 搜索结果支持服务端 `numPages` 分页、下拉刷新与底部继续上滑加载；
- 搜索页保留“改搜”和“视频/用户”互切，`@关键词` 仍表示用户搜索。

### 2. 首页推荐没有账号偏好

旧首页推荐请求未对 `/x/web-interface/wbi/index/top/feed/rcmd` 执行 WBI 签名，且没有稳定地带上登录 cookie 和设备身份；同时 `fresh_idx` 固定，无法按上游“初次/手动刷新/自动续页”语义请求。因此即使已经登录，也容易表现成与账号无关的固定内容。

处理如下：

- 新增统一请求 cookie：保留登录凭据，同时补齐持久 `buvid3`、`_uuid`；未登录时按 Web API 习惯补 `DedeUserID=0`；
- 首页推荐先从 `/x/web-interface/nav` 取得 WBI mixin key，再签名请求推荐接口；
- 对齐上游参数语义：初次 `fresh_type=0`、手动刷新 `3`、底部自动续页 `4`；手动刷新从 `fresh_idx=1` 重新计数，自动续页才递增；
- 登录、换号或退出后回到首页会重新拉取推荐，而不是继续使用上一账号的卡片；
- 推荐卡片展示服务端推荐理由、已关注提示和广告标识；底部支持加载更多并按 BV/aid 去重。

### 3. 动态、消息和账号列表条数/交互不足

旧页面在解析和绘制两个阶段均有硬截断：动态仅显示少量条目，消息仅显示少量条目；没有统一的滚动、刷新、续页和 cursor 模型。点击非视频动态或互动消息也只会出现静态提示，无法进入对应内容入口。

处理如下：

- `SectionScreen` 和 `ContentScreen` 改为真正可滚动的列表，支持下拉刷新与到底继续上滑加载；
- 动态以服务端 `offset + has_more` 游标续页（本地保留 page 计数用于诊断），单次最多解析 30 条；
- 回复、@、赞以服务端 `cursor.id/time/is_end` 续页；私信会话以最早会话时间戳续页，并处理部分接口缺失 `has_more` 的兼容情形；
- 消息列表显示四个明确标签：回复、@我、赞、私信；视频引用可进入视频详情，私信会话可进入会话页，非视频动态/互动会打开内容摘要而不再伪造“已读”；
- 账号的投稿、关注、收藏夹、收藏夹视频使用 `pn/ps` 分页；观看历史使用上游 `max/view_at` cursor 和 `ps=20`，显示观看进度/已看完状态；
- 账号资料可显示签名（没有签名时显示明确占位文案）。

### 4. 评论、动态与消息只有通用文本列表，无法还原客户端层级

本轮以提供的三张 Bilibili 客户端参考图，并对照上游 `VideoComment`、`DynamicArticleView`、`InboxFeed` 与 `InboxView` 的数据分层，重做了 Symbian 端的列表条目表达。目标是把作者、正文、媒体、时间、互动和未读状态保留为独立字段，而不是再拼成一行字符串。

- 评论：解析并保留头像 URL、等级、时间地点、点赞、回复数以及根评论下最多两条内嵌回复；UI 改为“圆形作者位 / 名称与等级 / 正文 / 时间地点与操作 / 灰色回复摘要”的结构。根评论点按仍进入既有楼中楼，楼中楼回复保持缩进。
- 评论头像：为避免评论滚动时产生大量 TLS 请求和 GL 纹理，当前绘制稳定的本地首字母圆形头像；接口头像 URL 已保留，可在后续经过真机内存验证后再启用真实头像纹理。
- 动态：请求使用当前仍在工作的 `/x/polymer/web-dynamic/v1/feed/all` 游标接口（`type=all`、`platform=web`、`features`、`offset`），不再依赖已对部分账号返回空/骨架数据的旧 `desktop/v1/feed/all` 路径。解析器兼容 `data.items`/`cards`/`list` 和 modules 的对象/数组两种形状，分别读取作者模块、动态模块和统计模块，再解析作者、发布时间、正文、视频/图文媒体描述、封面 URL、评论数、点赞数和 BV。UI 改为作者头、正文、媒体预览块和互动行；媒体预览块当前是本地绘制的安全占位，不会追加列表图片下载。
- 动态视频：只要服务端给出 BV，条目保留 `VideoContentItem + BV`。点击后走既有视频详情入口，详情页的播放键进入当前播放器；图文/文本动态则打开含正文的摘要页。
- 消息：改为图 3 所示的三个快捷入口加会话行。左侧“回复与 @”卡左/右区域分别进入回复和 @；中间进入收到喜欢；右侧进入现有私信会话。第三项没有伪装成“新增粉丝”，因为当前端尚未接入可靠的新增粉丝消息 API。会话/互动行显示本地头像位、名称、时间、摘要和未读红点。

### 5. 动态页只显示占位卡片（2026-08-27）

现象不是绘制层把数据遮住，而是动态请求完成后 `sectionItems` 为空/解析失败，`SectionScreen` 因而进入固定的 `DYNAMIC FEED` 占位分支。沿调用链检查后确认有两个高风险点：

- 请求仍指向上游旧的 `desktop/v1/feed/all` 路径，并携带已经不再作为主分页参数的 `page`；这与当前游标接口规范不一致，可能得到 HTTP 200 但没有可用动态数组；
- 动态返回的 modules 在不同版本中既可能是对象，也可能是数组，且 modules 内的作者、正文和统计是三个独立模块。旧解析器只按一种形状读取，遇到另一种形状会丢失整条动态的可展示字段。

本次修复改为当前游标式 `/x/polymer/web-dynamic/v1/feed/all`（登录 Cookie、`type=all`、`platform=web`、功能特性和 `offset`），并让解析器兼容对象/数组 modules、`items`/`cards`/`list` 列表和字符串/数字 offset。功能特性和游标本身只含 ASCII，直接按字节发送，避免 Qt 4.7 再次把 `%` 编码成 `%25`。动态视频仍保留 BV 引用，点击后走现有视频详情→播放入口；非视频动态继续进入正文摘要页。

## 合并后设备测试清单

### 前置

- 使用 Nokia 603 或目标 Symbian³ 设备；网络可访问 Bilibili。
- 分别准备未登录状态和有正常观看/关注/私信数据的测试账号。涉及发送私信、评论、关注等操作时请使用可控测试账号。
- 测试本轮内容时不执行实际播放；动态视频只确认能抵达既有视频详情/播放入口，播放器会话本身由其他任务合并后统一验证。

### 首页推荐

1. 未登录冷启动首页：应能显示推荐，卡片可正常滚动，不应因设备 cookie 缺失失败。
2. 登录后返回首页：应重新请求推荐；与退出后的卡片集合、推荐理由或关注提示应允许不同，不能继续复用旧账号卡片。
3. 下拉刷新：首页应替换列表并从手动刷新序列重新开始；滚动到底继续上滑应追加下一页，不应重复 BV，也不应丢掉已有卡片。
4. 切换热门、番剧、直播再回推荐：分类本身应正常工作，推荐页应重新走 WBI 请求。
5. 观察日志：`WW:HOME_WBI_READY` 后应出现推荐请求；失败时 UI 应显示“推荐签名准备失败”或可读的推荐错误，而不是静默空白。

### 搜索

1. 在首页搜索一个有明显结果的关键词（例如当前热门视频标题中的独特词）。结果标题、UP 主和 BV 应与关键词相关。
2. 搜索 `@` 加用户关键词：应进入“搜索用户”；右上“视频”可切回视频搜索，反向亦然。
3. 将结果滚到底继续上滑：有多页时应累加且去重；下拉刷新应回到第一页。
4. 关闭或限流网络、或触发服务端风控时：不得把 `v_voucher` 当作空结果；应显示“搜索响应被服务器拦截，请稍后重试”或签名准备失败。
5. 观察日志：应有 `WW:SEARCH_SUBMIT`、`WW:WBI_READY`、`WW:SEARCH_WIRE true false <长度>`、`WW:CONTENT_READY`；不应把关键词正文写入日志。若第二个布尔值为 `true` 或第一个为 `false`，请保留日志并反馈，表示关键词在线路上仍发生了二次编码或不一致。

### 账号与内容列表

1. 登录账号页：头像、昵称、UID、签名和关注/粉丝数据应正常显示；没有签名时显示占位文案。
2. 分别进入历史、收藏、稍后再看、我的投稿、我的关注。每页应可上下滚动，不再只显示首屏少量条目。
3. 历史记录：滚动到底续页后应继续请求 `max/view_at` cursor；已看完或进度文字应正确显示；下拉刷新应回到最新记录。
4. 收藏夹、投稿、关注、收藏夹内视频：超过 20 项时测试续页、去重、返回和再次进入。
5. 点击视频条目应进入视频详情；本轮只验证详情页入口，播放器测试由其他会话统一执行。

### 动态与消息

1. 动态页初始应显示实际关注动态，不应被固定 6 条 UI 截断；确认视频、图文和纯文本都能以作者头、正文、媒体预览和互动行显示。滚动、下拉刷新、到底加载更多均可使用。日志应出现 `WW:DYNAMIC_REQUEST`、`WW:DYNAMIC_WIRE false <长度>` 与 `WW:DYNAMIC_READY 200 0 <条数> ...`；若仍为空，保留 `WW:SECTION_FAILED` 的 HTTP/API code 和 parseError。
2. 动态中的 BV 视频点按应进入对应视频详情（既有播放入口）；图文/文本动态点按应显示原动态正文摘要，不能错误显示“消息已读”。实际播放留给播放器任务合并后的统一测试。
3. 动态媒体预览块当前不下载真实封面：确认网络慢、连续滚动和返回页面时不会因缩略图纹理触发卡顿、闪退或泄漏；该块仍应明确标出“视频”或“图文”。
4. 消息页顶部应为“回复与 @ / 收到喜欢 / 私信会话”三张快捷卡。左卡左侧点按进入回复、右侧点按进入 @；中、右卡分别进入赞和私信。每次切换都应重置对应 cursor 和列表，不应混入前一类数据。
5. 会话/互动行应显示名称、时间、消息摘要、本地圆形头像位和未读红点（有未读的私信）。每个消息入口测试滚动、刷新和续页；私信会话点击后可进入会话并使用“发私信”入口。
6. 对空数据、登录过期、HTTP 非 200 和 API 非 0：应保留已加载的追加列表或显示可读状态，不能闪退或无限加载。

### 评论结构

1. 打开任意有较多评论的视频，验证每条根评论依次出现作者圆形头像位、昵称、LV 徽标（服务端有等级时）、正文、时间/地点、点赞/回复操作行。
2. 找到带 `rcount` 且服务端内嵌 `replies` 的根评论：应出现浅灰回复摘要，最多两条预览和“共 N 条回复 >”。没有内嵌回复数据时不能出现空灰框。
3. 点按根评论：应进入既有楼中楼列表；楼中楼回复保持缩进、作者/正文/时间/点赞信息完整。返回后应仍在评论列表，滚动和续页状态不应异常。
4. 连续滚动评论、下拉刷新、返回再进入：确认本地头像位不发起大量图片请求，且评论文本、表情 Unicode、长昵称、缺失地点/等级都不重叠或闪退。
